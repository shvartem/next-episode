# Зависимости и контракты модулей

## Циклические зависимости при импортах

Граф импортов файлов проекта должен быть ацикличным как внутри слоя, так и между слоями. Если файл A прямо или через другие файлы импортирует B, любой путь импортов из B обратно в A образует запрещённый цикл. При проверке учитываем также реэкспорты и `import type`.

Например, если `index.ts` реэкспортирует A и B, а A импортирует B через этот `index.ts`, возникает цикл `A → index.ts → A`. Если направление зависимости A → B допустимо, A импортирует B напрямую.

Импорт типа исчезает при сборке, но связывает исходные файлы. Например, View импортирует Presenter, поэтому общий тип `Props` оба файла импортируют из `types.ts`.

## Направление зависимости внутри слоя

Если файл Б меняется чаще файла А, Б может использовать контракт А. Обратная зависимость заставила бы устойчивый модуль учитывать детали более изменчивого. Устойчивость оцениваем по причинам изменений. Например, общий список зависит от требований к отображению списка, а экран поиска — ещё и от правил выбора сериала. Экран импортирует список и передаёт обработчик выбора через пропсы. При изменении действия на экране достаточно заменить обработчик.

## Контракт при создании модуля

Когда у устойчивого модуля появляется первый потребитель, определяем публичный контракт исходя из потребностей вызывающего кода. Для функции достаточно типизированной сигнатуры и согласованного поведения. Фиксируем входные данные, результат и, где применимо, поведение при ошибках и отмене. Все потребители обращаются к модулю через этот контракт. Детали конкретной реализации остаются внутри модуля.

## Порядок замены реализации

1. Проверить места вызова и определить, на какое поведение рассчитывают потребители. Если действующий контракт уже скрывает заменяемую деталь, перейти к замене реализации.
2. Если потребители используют эту деталь напрямую, выделить контракт на текущей реализации. Перевести на него затронутые места вызова и проверить прежнее поведение. Завершить этот этап до замены реализации.
3. Заменить реализацию внутри модуля и повторить те же проверки. Если потребителям требуется новое поведение, согласовать это как отдельное изменение контракта.

Например, задача поиска вызывает `showsRepository.getShowsList(query, signal)`. При переходе с `fetch` на `axios` репозиторий отвечает за преобразование ответа клиента в результат поиска. До и после замены проверяем, какие данные получает задача при успехе, какую ошибку получает при неуспешном ответе и как завершается отменённый запрос. Сохранение этих условий позволяет заменить клиент без изменений в задаче и Presenter.
